# SevenMirror 用户 Alpha 产品信息架构

> 状态：历史 Alpha 方案，保留追溯，不代表本轮最终设计已批准
> 当前重设计入口：[三端产品重设计草案](PRODUCT_REDESIGN.md)。本文的旧页面结构、实施顺序及阶段性门禁描述不直接用于新一轮实施，当前能力状态以 STATUS 为准。
> 更新时间：2026-08-31
> 适用范围：Server 管理端、Android 应用、Chrome 扩展
> 目标版本：面向能够自托管服务的个人用户 Alpha

## 1. 阶段结论

SevenMirror 已完成多设备通知镜像的主要协议和工程闭环，但当前 Server CLI、Android `MainActivity`、Chrome Popup 和 Options 仍是工程验收入口。用户 Alpha 不沿用这些页面的结构，而是围绕「部署服务、加入设备、确认同步、处理通知、恢复连接」重新组织三端体验。

本阶段交付的是可供目标用户实际使用的产品，不把内部协议、安全扫描或发布制品状态包装成用户功能。第三方应用通知在独立安全评审和真机发布门禁关闭前仍不联网；正式页面不得提供绕过该限制的开关。

已确认的首版产品决策：

- 新设备只能由 Server 管理网页批准；Android 和 Chrome 只能提交并查看自己的申请状态；
- Android 和 Chrome 只读查看工作区设备的 authority-signed 名称，不能重命名、批准、拒绝或移除其他设备；
- Chrome 工具栏角标表示尚未点开查看的新通知数，不表示当前活动通知总数；
- Android 首次设置默认不预选应用，由用户明确选择，并提供「选择全部普通应用」；
- Server 第一版显示申请、批准、最近成功认证、最近活动和移除时间；最近活动最多每分钟落盘一次，不伪装成严格实时在线；
- Android 通知权限先采用全局默认加应用级覆盖：全局分别控制普通操作、回复和清除，应用级提供「允许所有操作」「只允许查看」「自定义」。

设备显示名称采用 authority-signed 全工作区权威名称，由 Server 管理端修改并通过 certificate transition 和下一份 signed roster 同步到各端。Android 和 Chrome 只读展示该名称，不建立本地别名或第二套名称存储。

## 2. 目标用户与职责

用户 Alpha 只有一种产品角色：管理自己私有实例的个人用户。这个人在不同场景中承担三个职责：

- **实例管理员**：部署 Server，允许新设备加入，撤销不再使用的设备，维护备份；
- **手机用户**：在 Android 上授予通知访问权限并控制哪些通知可以同步；
- **浏览器用户**：在 Chrome 查看、回复、操作和清除来自手机的通知。

Alpha 不引入团队、组织、多管理员 RBAC、远程项目方账号或项目方托管服务。

## 3. 跨端核心任务

### 3.1 首次设置

```text
部署 Server
  → 初始化私有空间
  → 按需启动本机管理端
  → 允许一台 Android 加入
  → Android 提交申请
  → 管理端批准 Android
  → Android 完成通知访问设置
  → 允许一个 Chrome 加入
  → Chrome 提交申请
  → 管理端批准 Chrome
  → 两端显示可以同步
```

配对码只用于提交加入申请。客户端必须把「申请已提交」和「设备已批准」显示为两个不同阶段，不能在提交成功后提前显示可用。

### 3.2 日常使用

- Android 首页回答「通知当前是否可以同步」以及用户下一步需要做什么；
- Chrome Popup 以当前通知为主，连接状态只占次要位置，并能展开通知、回复和执行全部可用操作；
- 点击 Chrome 系统通知主体时继续打开独立 interaction 页面，但它与 Popup 详情共享同一套展示和操作能力，不形成双轨实现；
- Server 管理端只处理实例和设备管理，不展示通知标题、正文、回复或操作内容。

### 3.3 故障恢复

三端使用同一组用户可理解的状态：

| 产品状态 | 用户含义 | 首要操作 |
|---|---|---|
| 需要设置 | 设备尚未加入私有空间 | 开始设置 |
| 等待批准 | 加入申请已提交 | 联系实例管理员或刷新状态 |
| 正在连接 | 设置有效，正在连接私有服务 | 等待 |
| 可以同步 | 连接和必要权限均正常 | 无 |
| 无法连接 | 暂时联系不到私有服务 | 检查服务地址和服务运行状态 |
| 访问已移除 | 管理员已撤销当前设备 | 重新加入 |
| 设置需要修复 | 本地身份或安全设置无法继续使用 | 撤销旧设备后重新加入 |
| 缺少通知访问权限 | Android 无法读取通知 | 打开系统设置 |

用户界面不显示 `SNO1`、roster、HPKE、replay、cursor、outbox、裸枚举、内部 ID 或原始异常。详细技术信息只进入开发构建或脱敏诊断导出。

## 4. Server 管理端

### 4.1 进程和信任边界

管理网页由独立的 `admin-web` 进程提供，不挂载到 relay 的公开业务 Handler，也不让 authority private key 进入 relay 热路径。

Alpha 边界：

- 默认不启动，管理员需要时显式运行；
- 默认只监听 loopback；非 loopback 明文监听必须拒绝；
- 远程使用通过 SSH 端口转发，或通过独立 HTTPS 管理域名和反向代理；
- 不与设备注册、Membership 或 WebSocket API 共用管理员会话；
- 页面资源随二进制提供，不加载 CDN、遥测或第三方脚本；
- authority rotation、workspace restore 和不可逆全量清理在 Alpha 继续由本机 CLI 完成，不放入网页。

### 4.2 管理员会话

首个 Alpha 使用按需、短生命周期会话，不建立长期管理员账号系统：

1. `admin-web` 启动时生成至少 192 bit 的一次性登录码；
2. 登录码只在管理员终端显示一次，不进入 URL、数据库、访问日志或支持包；
3. 登录码默认十分钟过期且成功使用后立即失效；
4. 登录成功后创建随机、仅存内存的 HttpOnly、SameSite=Strict 会话；
5. 管理进程重启后所有会话失效；
6. 所有状态变更使用 POST、严格 Origin 校验和独立 CSRF token；
7. 登录失败和管理操作具有独立限速；
8. 页面设置严格 CSP、禁止 framing、禁止跨源读取并使用 query-free 路径。

通过 HTTPS 使用时会话 cookie 必须设置 Secure。通过 SSH 转发访问 loopback HTTP 时，安全边界依赖本机 loopback 和 SSH 隧道，管理端不得直接暴露到局域网或公网。

### 4.3 导航

#### 概览

回答：服务是否可用、有哪些设备需要处理、最近是否有可用备份。

显示：

- 服务版本和运行状态；
- 已批准 Android／Chrome 数量；
- 待批准申请数量；
- 已移除设备数量；
- 最近一次成功设备认证和最近活动摘要；
- 数据目录和备份状态的用户化摘要；
- 需要管理员处理的事项。

不显示通知内容、队列 frame、密文或完整设备标识。

#### 设备

提供：

- 生成 Android 或 Chrome 加入码；
- 可选预先绑定用户可见设备名称；
- 一次性展示加入码及剩余有效时间；
- 查看待批准、已批准和已移除设备；
- 对待批准申请执行批准或拒绝；
- 批准申请时使用按设备类型固定的最小角色模板；
- 修改设备的用户可见名称；
- 移除设备，并在确认框中说明该设备将停止同步且需要重新加入；
- 显示申请时间、批准时间、最近成功认证时间、最近活动时间和移除时间。

页面中的「移除设备」在后端首先执行 durable revocation，并保留防止旧凭据恢复访问所需的记录，不等同于直接硬删除数据库行。真正的数据清理属于独立维护操作。

普通流程不让用户编辑裸 role 枚举。Android 和 Chrome 的权限模板由产品定义，角色细节只出现在开发诊断中。新设备的批准、拒绝和移除只存在于 Server 管理网页；客户端无对应管理入口。

#### 数据与恢复

首个切片只提供只读状态和明确操作指引：

- 当前数据位置；
- 最近一次已验证备份状态；
- 创建备份的本机命令；
- 恢复必须停止服务且使用 CLI 的说明；
- authority key 外部备份提醒。

网页不接受任意服务器文件路径，不在线执行 workspace restore。

#### 关于

显示版本、许可证、文档入口和脱敏诊断导出入口。诊断不包含管理员登录码、pairing code、transport credential、设备完整 ID、authority private key 或业务明文。

### 4.4 响应式与无障碍

管理端以桌面浏览器为主，在窄屏仍可完成紧急撤销。所有功能必须支持键盘；焦点、错误和成功不能只通过颜色表达；危险操作使用明确对象名称和结果说明。

## 5. Android 正式信息架构

### 5.1 首次设置流程

首次设置使用可恢复的分步流程，而不是在首页堆叠所有字段：

1. **欢迎**：说明 SevenMirror 将通知同步到用户自己的 Chrome；
2. **连接私有服务**：输入 HTTPS 地址并进行本地格式校验；
3. **加入设备**：输入管理员提供的一次性加入码和设备名称；
4. **等待批准**：显示申请状态，可安全退出后恢复；
5. **通知访问**：解释读取范围并打开 Android 系统设置；
6. **选择应用**：默认不预选应用，用户逐项选择，或显式选择全部普通应用；
7. **准备完成**：只有成员批准、凭据生效、通知访问和应用选择均满足后才显示。

Camera QR 属于后续切片，必须承载 authority registration 数据，不恢复历史 `sntrust1:` 模型。

### 5.2 主导航

手机宽度使用底部导航；大屏根据 Material 3 adaptive guidance 使用 navigation rail。

#### 首页

- 当前是否可以同步；
- 私有服务和本设备的用户可见名称；
- 通知访问状态；
- 最近连接问题及可执行下一步；
- 前往应用同步设置。

首页不展示 synthetic 测试、outbox 数量、测试通知、内部 key 或协议状态。

#### 应用

用于第三方通知开放后的逐应用控制：

- 默认不选择任何应用，首次设置提供「选择全部普通应用」但不自动触发；
- 可同步应用列表，以及已选择应用数量；
- 每个应用的允许／阻止状态；
- 搜索、普通应用／系统应用筛选和批量选择；
- 正文显示、持续通知和静默通知等全局默认；
- 普通操作、回复和从 Chrome 清除分别具有全局默认；
- 应用级提供「允许所有操作」「只允许查看」「自定义」覆盖；
- 自定义模式可以分别控制普通操作、回复和清除。

Android 决定哪些通知数据可以离开手机。Chrome 的本地隐藏或静默设置不能改变 Android 上传边界，也不能把「本地不显示」描述成「没有同步」。

在第三方通知门禁关闭期间，此页面不提供隐藏启用开关。开发构建中的 synthetic 验证入口移入独立诊断页面。

#### 设备

- 查看当前工作区 Android 和 Chrome 的数量、名称、类型和最近活动状态；
- 区分当前设备；
- 只读展示 authority-signed 设备名称；
- 不提供设备重命名、批准、拒绝或移除；
- 当前 Android 的申请状态仍由 onboarding／首页展示。

#### 设置

- 私有服务地址，只读显示并通过重新加入流程变更；
- 本设备名称；
- 通知访问快捷入口；
- 数据和隐私说明；
- 重新加入／移除此设备；
- 关于、许可证和脱敏诊断。

transport credential rotation 不作为普通用户独立任务展示；需要轮换时由用户可理解的「更新设备访问」恢复流程承载。

### 5.3 Android 设计系统

- Jetpack Compose 和稳定版 Material Design 3；
- 单一 theme 定义颜色、排版、形状和间距；
- edge-to-edge、动态颜色、深色模式；
- 字体缩放、TalkBack、横屏和合理大屏适配；
- 触控目标至少 48 dp；
- 页面提供加载、空、离线、权限缺失、失败和恢复状态；
- 用户可见文本全部来自 Android resources，简体中文和英文同步维护。

## 6. Chrome 正式信息架构

### 6.1 Popup

Popup 的核心任务是查看和处理当前通知，而不是运行测试。

结构：

1. 紧凑状态栏：来源设备筛选、当前连接问题和当前活动通知总数；
2. 当前通知列表：按更新时间倒序；
3. 通知项：来源设备、应用、标题、正文摘要、时间和是否新到达；
4. 通知详情：完整正文、全部可用操作、回复和从手机清除；
5. 空状态：没有当前通知、等待批准、无法连接或尚未设置；
6. 页尾入口：设置。

工具栏 Badge 表示尚未点开查看的新通知数，可以在设置中关闭。用户点开某条通知的详情后，该条标记为已查看并减少角标；仅打开 Popup 浏览列表不把任何通知标记为已查看。通知更新是否重新标记为新到达，应以正文、操作或 revision 发生用户可见变化为准，纯恢复和重复投递不增加角标。

Popup 不展示 Worker 启动次数、关闭审计、E2EE 测试、fingerprint 或 synthetic 操作。

### 6.2 Options

采用侧边导航或窄屏分区导航：

#### 连接

- 首次加入流程；
- 私有服务地址；
- 当前 Chrome 设备名称；
- 当前设备的等待批准、可以同步、无法连接、访问已移除和需要修复状态；
- 重新加入。

#### 设备

- 查看当前工作区 Android 和 Chrome 的数量、名称、类型和最近活动状态；
- 区分当前设备；
- 只读展示 authority-signed 设备名称；
- 不提供设备重命名、批准、拒绝或移除。

#### 通知

- Chrome 通知权限状态；
- 来源 Android 列表和本地筛选；
- 新通知 Badge 开关；
- 是否固定显示「清除」快捷按钮；
- 正文、头像、静默通知和浏览器侧隐藏等个性化选项；
- 明确说明浏览器侧隐藏只影响本机展示，不改变 Android 上传范围。

#### 快捷操作

继续使用独立 `shortcuts/index.html`，从 Options 导航进入。规则只描述用户看得到的应用和操作标题，不展示 opaque action ID。

#### 数据与隐私

- 本地保存内容说明；
- 清除本地镜像状态；
- 移除此 Chrome 设备；
- 脱敏诊断导出。

#### 关于

版本、许可证和项目文档。

### 6.3 Interaction 页面

现有独立 interaction 页面继续作为点击 Chrome 系统通知后的完整操作入口，但与 Popup 通知详情共享 presentation component、read model 和 operation command，不复制业务实现：

- 始终显示来源 Android、来源应用和通知摘要；
- 与 Popup 一样展示来源公开的全部可用操作；
- 回复输入绑定当前 revision；
- 明确显示发送中、已完成、已失效、手机不可用和结果无法确认；
- 通知更新后提示用户基于最新内容重新操作；
- 不把本地 socket 接受解释为手机已经执行。

### 6.4 Chrome 设计约束

- 使用原生 HTML／CSS／TypeScript 和现有轻量架构，不引入大型 UI 框架；
- 使用 CSS design tokens 统一颜色、排版、间距、圆角和状态；
- 支持键盘、可见焦点、屏幕阅读器和 200% 缩放；
- 用户文案全部通过 `chrome.i18n`；
- Release 默认界面不包含诊断和 synthetic 控件。

## 7. 三端状态与数据边界

UI 使用独立 presentation model，不直接展示协议枚举。业务层必须输出稳定的结构化状态和用户可执行操作，页面只负责本地化和展示。

同一事实只保留一个定义点：

- membership 和 transport 状态由现有业务 store／coordinator 提供；
- Server 设备成员状态由 admission store 提供；
- Android 权限状态由系统 API 提供；
- Chrome 当前通知由 notification state store 提供；
- Chrome 新通知计数由同一 notification state store 中的 presentation metadata 派生，不能用 Worker 内存另算；
- Server 最近活动使用经过采样的 durable 时间，最多每分钟为同一设备写入一次；
- UI 不建立第二套成员、连接或通知状态数据库。

新增 read model 可以组合既有状态，但不得复制 authority、credential、roster 或 notification lifecycle 规则。

设备批准、撤销和加入码签发也只能有一个业务实现点。实现 UX-002 前，应把 `cmd/admin` 中对应用例提取为 Server 内部管理应用服务，由 CLI 和管理网页分别作为命令行与 HTTP 适配器调用；管理网页不得执行 CLI 子进程，也不得复制 authority key 加载、角色模板、事务或签名逻辑。只为转发参数而存在的包装层不纳入设计。

## 8. 实施切片

### UX-001：Server 管理端安全骨架

- 独立 `cmd/admin-web`；
- loopback-only 配置；
- 一次性登录和内存会话；
- CSRF／Origin／CSP／frame 防护；
- 概览、设备列表、时间状态和空状态；
- 不提供状态变更。

验收：通过真实浏览器登录后能看到不含敏感内容的 workspace 和设备摘要；relay 的公开 Handler 没有新增管理路由。

### UX-002：Server 设备管理闭环

- 生成加入码；
- 待批准列表；
- 提取由 CLI 和网页共享的唯一管理业务用例；
- Android／Chrome 固定权限模板批准；
- 申请拒绝、设备名称修改和移除确认；
- 一次性 secret 展示边界。

验收：一台新设备从申请到批准全程无需管理员手写设备 reference，撤销后客户端显示访问已移除。

### UX-003：Android onboarding 和首页

- 正式主题和 adaptive scaffold；
- 可恢复首次设置；
- 首页状态和只读设备列表；
- 通知访问引导和默认不预选的应用选择；
- debug-only 诊断入口分离。

验收：全新安装可以完成加入、等待批准、授权和可同步状态；Release 页面不出现 synthetic 或协议术语。

### UX-004：Chrome Popup 和连接设置
