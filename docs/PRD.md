# 通知镜像系统产品需求文档（PRD）

> 文档状态：用户 Alpha 产品化阶段  
> 产品定位：开源、完全自托管、只专注 Android → Chrome 通知镜像与通知操作  
> 覆盖端：Linux 服务端、Chrome 扩展、Android 应用  
> MVP 原则：不做文件传输、剪贴板、远程控制、短信管理器等横向功能

---

## 1. 背景与目标

### 1.1 问题

用户在桌面端使用 Chrome 时，需要频繁查看和操作 Android 手机上的通知。现有产品通常存在以下至少一个问题：

- 依赖厂商云服务，不能完全自托管；
- 核心功能需要订阅或付费解锁；
- 功能庞杂，安装、配置和权限边界不清晰；
- 用户无法控制通知内容的存储、传输和保留周期。

### 1.2 产品目标

建立一个极简通知镜像系统，使用户能够：

1. 在 Android 收到通知后，及时在 Chrome 中看到镜像通知；
2. 在 Chrome 中触发原通知提供的操作，例如“回复”“标记已读”“归档”；
3. 从 Chrome 关闭镜像通知时，同步清除 Android 上对应的通知；
4. 完全使用用户自建 Linux 服务端中转，不依赖项目方云服务；
5. 免费、开源，不设置任何付费解锁功能。

### 1.3 MVP 成功标准

- 任意已配对 Android 的通知在正常在线网络下，95% 在 3 秒内出现在所有在线 Chrome；
- 每条通知明确标注来源 Android 设备，多个来源设备的通知不会发生 ID 冲突；
- Chrome 能展示并调用 Android 原通知公开的操作项，例如短信/聊天通知的“标记为已读”、邮件通知的“归档”，并支持带文本输入的回复操作；
- 任一 Chrome 主动关闭通知后，Android 对应通知被清除，其他 Chrome 上的镜像也同步消失；
- Android 侧移除或更新通知后，所有 Chrome 最终收敛到一致状态；
- 断线重连后不会无止境重复弹出旧通知；
- 服务端可通过容器方式在一台 Linux 主机上独立部署；
- 端到端加密为 MVP 强制要求，服务端不能读取通知正文、回复文本、图标、头像或操作内容；
- 服务端默认关闭公开注册，只有实例管理员明确批准的设备才能接入；
- 不依赖 FCM、Firebase 或项目方运营的中继服务即可完成核心链路。

### 1.4 非目标

以下功能不属于当前阶段：

- iOS 支持；
- 独立的文件、图片或链接推送（通知所属应用图标和头像除外）；
- 剪贴板同步；
- 通讯录、完整短信列表或通话记录管理；
- 手机屏幕镜像、远程控制；
- 跨设备输入法；
- 浏览器之间同步非通知类数据；
- 公网长期开放的多租户管理平台；
- 多管理员账号、团队 RBAC 和在线 authority rotation；
- 通知历史搜索、统计或长期归档；
- 项目方托管的 SaaS 服务；
- 团队、组织、RBAC、审计平台；
- Safari、Firefox 或 Edge 的专项适配（兼容 Chromium 的 Edge 可后续验证）。

## 2. 关键产品决策与约束

### 2.1 “完全自托管”的定义

核心业务链路必须为：

```text
Android 应用 ←→ 用户的 Linux 服务端 ←→ Chrome 扩展
```

- 项目方不提供账号中心、推送中继或遥测服务；
- 核心功能不得依赖 FCM；
- Android 与 Chrome 均由用户配置自己的服务端地址；
- 更新检查、崩溃上报和使用统计默认关闭，且不能影响核心功能；
- 所有运行时依赖都应能由用户自行部署或打包在单个服务端发行物中；
- 实例默认是私有工作区，不提供公开注册入口。拥有服务端地址不代表有权注册或连接设备。

### 2.2 Android 通知操作的实现边界

Chrome 不能直接执行 Android 的 `PendingIntent`。正确链路是：

1. Android 读取通知及其可执行操作；
2. Android 为每个操作生成当前通知生命周期内有效的操作标识；
3. Chrome 将“通知标识 + 操作标识 + 可选回复文本”发回 Android；
4. Android 在本机调用原通知的 `PendingIntent`，文本回复通过 `RemoteInput` 注入。

因此：

- 操作只能在 Android 设备在线且原通知仍有效时执行；
- 部分应用禁止、遗漏或自定义了通知操作，系统无法保证全部兼容；
- Android 重启、应用被强制停止、通知已撤回或 `PendingIntent` 失效时，操作应明确失败，不得假装成功。

### 2.3 Chrome 展现限制

- 系统通知用于即时提醒；
- 点击系统通知主体始终打开独立的小型通知交互窗口，展示全部操作项和回复输入，不在普通浏览器窗口新增标签页。该窗口不是工具栏 Popup，失焦后仍保留，关闭窗口不代表清除手机通知；
- Chrome 系统通知最多展示两个操作按钮，快捷按钮不承担完整能力发现；
- 默认开启「始终显示『清除』按钮」，用户可以关闭；开启后「清除」固定占用一个按钮；
- 用户可以添加并排序快捷操作规则。符合规则的来源操作按规则顺序优先展示；「更多」是不可删除的最低优先级候选项，仅在仍有未直接展示的操作时出现；
- 来源通知只有一个操作时直接显示，不要求匹配快捷规则；多个操作且没有规则命中时显示「更多」；
- 快捷规则只影响排序，不得重命名来源操作，也不得绑定随通知 revision 变化的 opaque action ID；
- 需要文本输入的操作按钮只负责打开并聚焦完整回复界面，不假设系统通知支持内联文本框；
- Manifest V3 Service Worker 可能被挂起，连接、关闭原因标记与重连设计不能依赖其永久存活。

### 2.3.1 产品界面与 Android Material Design 3

当前 Android `MainActivity`、Chrome Options 和 Popup 只承担能力验证、诊断和人工验收，不构成最终产品的信息架构、视觉设计或交互先例。不得把现有单页堆叠控件当作可持续扩张的产品页面。

Android 正式产品界面必须使用 Jetpack Compose，并全面遵循实施时稳定版 Material Design 3 与 Android 官方质量规范：

- 先确定正式信息架构、核心用户任务和导航模型，再替换临时验证页面；
- 使用集中式 Material 3 主题、颜色、排版、形状和组件体系，不在业务页面散落视觉常量；
- 支持 edge-to-edge、深色模式、动态颜色，以及手机、横屏和合理大屏宽度下的自适应布局；
- 满足无障碍语义、对比度、字体缩放、触控目标、键盘／辅助技术操作和非颜色状态表达；
- 加载、空状态、离线、权限缺失、失败和恢复都使用面向用户的明确反馈，不显示协议术语、裸枚举、内部 ID 或原始异常；
- 普通用户流程与开发诊断入口分离，synthetic 测试、outbox 计数和协议验证控件不得进入正式默认界面。

Material 3 产品化改造不是对当前页面换色或替换组件。P1 等协议与恢复阶段应优先保持 UI 无关的状态和业务边界，只为当前验收增加最小临时控件，避免形成对临时页面的路径依赖。

三端正式信息架构、导航、状态词汇和实施切片以 [SevenMirror 用户 Alpha 产品信息架构](PRODUCT_INFORMATION_ARCHITECTURE.md) 为准。

### 2.4 删除语义

MVP 采用明确规则：

- 用户主动关闭任一 Chrome 的镜像通知：请求清除来源 Android 上的原通知；
- Android 清除成功后发布最终删除事件，所有 Chrome 关闭对应镜像通知；
- Android 原通知被用户或应用清除：所有 Chrome 关闭对应镜像通知；
- Android 原通知不可清除时，发起操作的 Chrome 显示失败并给出原因，其他 Chrome 保持原状态。「不可清除」指平台不接受通知监听器发起的单条取消，即常驻通知（`FLAG_ONGOING_EVENT`）；仅被排除在「清除全部」之外、但用户仍可自己划掉的通知不属此列，必须可以远程清除；
- 因 Chrome 浏览器退出、系统通知中心自动回收、扩展重载造成的不可确认关闭，不应误删 Android 通知；
- 在扩展弹窗点击“从列表移除”与“同时从手机清除”必须区分。MVP 只提供后者，避免各 Chrome 状态分叉。

### 2.5 多 Android、多 Chrome 与全局状态（P0）

> 最新产品修正：每台 Android 可以独立选择接收浏览器，获批成员不再默认等于该手机的发送目标。本文其他章节中「所有 Chrome」「广播」「扇出」的通知同步范围，均以本节定义的有效接收集合为准，不表示向全部工作区成员发送。该需求已进入重设计，生产端尚未完成实现。

有效接收集合是「当前有效、具备接收资格的工作区成员」与「来源 Android 已保存选择」的交集。发送选择是 Android 的业务限制，不替代管理员成员批准，也不能由浏览器本地隐藏设置替代。新配置和没有显式记录的旧配置默认空选择；已有用户选择原样保留，包括显式保存的空选择。旧版隐式全成员发送不算显式选择，新批准成员不自动加入。设置入口及取消选择后的已发内容边界见 [重设计草案](PRODUCT_REDESIGN.md)。

- 一个私有工作区允许同时注册多台 Android 和多台 Chrome；MVP 不设置产品层面的固定设备数量限制，由服务端配置资源上限；
- 每台 Android 只向其有效接收集合内的 Chrome 同步通知，设备离线不改变用户选择；补发与当前快照也须遵守发送范围。取消选择不保证撤回此前已发出或已在服务端排队的内容；
- 通知全局主键为 `(sourceDeviceId, notificationId)`，显示和操作时必须始终携带来源设备；
- Android 是其通知内容及生命周期的最终权威来源，服务端负责扇出和短期状态协调；
- 任一 Chrome 发起操作后，命令只路由到来源 Android；操作结果及后续通知更新/删除广播给所有 Chrome；
- 多个 Chrome 同时操作同一通知时，Android 按接收顺序串行校验。第一个操作导致通知更新或移除后，绑定旧版本的后续操作必须失败；
- 每个 Chrome 有独立确认游标和本地展示状态，但共享同一通知版本与最终删除状态；
- 新加入的 Chrome 只能获取加入后仍处于活动状态的通知快照，不默认获得历史通知。

## 3. 用户与使用场景

### 3.1 目标用户

- 拥有 Android 手机并长期在 Chrome 中工作的个人用户；
- 能够自行部署 Docker 容器或 Linux 服务的技术用户；
- 对隐私、数据主权和第三方云依赖敏感的用户。

### 3.2 核心场景

#### 场景 A：查看通知

手机收到聊天、邮件或系统通知，Chrome 在数秒内显示包含应用名、标题和正文的系统通知。

#### 场景 B：快速回复

手机收到支持 `RemoteInput` 的消息通知，用户在 Chrome 点击“回复”，输入文本并提交；Android 调用原通知回复动作，Chrome 显示成功或失败结果。

#### 场景 C：执行普通操作

用户在 Chrome 对邮件通知点击“归档”或“标记已读”；操作由 Android 原应用执行，结果回传 Chrome。

#### 场景 D：清除通知

用户关闭 Chrome 通知，手机上的对应通知也被清除。反向清除同样生效。

#### 场景 E：短暂离线

手机或 Chrome 短暂离线。恢复连接后同步当前仍有效的通知状态，不重复弹出已经处理过的通知，也不复活已删除通知。

#### 场景 F：多设备扇出与一致清除

用户的多台 Android 都向同一私有工作区同步通知。所有已授权 Chrome 收到通知并显示来源设备；用户在其中一台 Chrome 清除通知后，来源 Android 和其他 Chrome 上的对应通知均消失，而其他 Android 上无关通知不受影响。

## 5. 详细功能需求

## 5.1 Android 应用

### AND-001 首次引导与服务端配置（P0）

用户可：

- 输入 `https://` 服务端地址，或扫描 Chrome/服务端生成的二维码；
- 检查服务端可达性和 TLS 状态；
- 完成设备加入申请并等待 Server 管理网页批准；
- 为设备设置可识别名称；
- 查看当前连接状态；
- 默认不预选应用，由用户明确选择同步应用，并提供「选择全部普通应用」。

验收条件：

- 非 HTTPS 地址默认拒绝，开发模式可显式允许局域网 HTTP；
- 地址错误、证书错误、鉴权失败须提供不同错误提示；
- 配对凭据安全保存在 Android Keystore 支持的加密存储中；
- 退出配对后，本地凭据和待发送敏感数据被清除。

### AND-002 通知访问授权（P0）

应用应引导用户进入系统设置，为 `NotificationListenerService` 授权，并实时显示授权状态。

验收条件：

- 未授权时不得显示“同步正常”；
- 权限被撤销后停止上传并提示用户；
- 应解释权限用途及会读取的数据类型。

### AND-003 捕获新增与更新通知（P0）

监听 Android 通知新增、内容更新和移除事件。

应采集的最小字段：

- 本机生成的稳定通知实例 ID；
- 来源设备 ID；
- Android `key` 的本地映射；
- 包名、应用显示名称；
- 标题、正文、扩展正文；
- 发布时间、更新时间；
- 通知分组信息、是否为分组摘要；
- 是否可清除、是否持续驻留、是否为静默通知；
- 来源应用图标；
- 通知大图标、会话头像或联系人头像（存在且 Android API 可读取时）；
- 是否包含正文图片或富媒体；正文图片本身不在 MVP 中传输；
- 可执行操作列表；
- 内容版本号。

默认不采集：

- 与通知显示无关的完整 `extras`；
- 联系人数据库；
- 通知应用的账号凭据；
- 不执行同步所必需的任意后台数据。

### AND-004 通知过滤和规范化（P0/P1）

P0 默认规则：

- 首次设置默认不选择任何应用，用户可以逐项选择或显式选择全部普通应用；
- 不镜像本应用自己的常驻连接通知；
- 持续通知、前台服务通知默认不同步，用户可以按应用显式开启；
- 静默通知是否同步由全局默认控制；同步后在 Chrome 以静默方式展示，不主动播放声音；
- 抑制明显的重复更新；
- 同一个 Android 通知更新时，更新 Chrome 现有镜像，不创建无穷多个通知；
- 分组摘要和子通知不得造成明显重复；默认优先同步可操作的子通知；
- 通知包含正文图片、消息图片或其他富媒体时，不上传原图，在正文对应位置或末尾使用统一的 `[图片]` 占位符；
- 应用图标和可读取的通知头像属于 MVP 同步范围，不受正文图片占位规则影响。

P0 用户规则：

- 按应用允许或禁止同步；
- 全局分别控制普通操作、回复和从 Chrome 清除；
- 应用级提供「允许所有操作」「只允许查看」「自定义」；
- 自定义模式分别控制普通操作、回复和清除；
- 对指定应用仅显示“收到一条通知”，不传标题和正文；
- 按应用开启持续通知同步。

P1 用户规则：

- 控制头像展示；
- 系统敏感通知的默认阻止列表可配置。

### AND-004A 图标与头像处理（P0）

- Android 将来源应用图标渲染为标准 PNG 或 WebP，不直接发送任意 Drawable/资源引用；
- 若通知提供大图标、`Person` 图标、会话头像或消息发送者头像，优先提取最贴近当前通知语义的一张头像；
- 图标与头像在缩放后建议最大为 256×256，单个文件硬上限建议 128 KiB；
- 动图只取静态首帧；SVG、外部 URL 和无法安全解码的格式不传输；
- 媒体字节与通知正文一起端到端加密，服务端只能看到受限的密文大小和路由元数据；
- 使用内容哈希在同一来源设备内去重，更新未变化的应用图标时不重复上传；
- 提取或解码失败时回退到默认设备/应用图标，不影响文本通知同步。

### AND-005 提取操作项（P0）

每个操作至少包含：

- 临时操作 ID；
- 用户可见标题；
- 是否需要文本输入；
- `RemoteInput` 的必要元数据，仅保存在 Android 本地；
- 对应 `PendingIntent`，仅保存在 Android 进程/本地短期映射中；
- 失效时间或随通知销毁而失效的状态。

要求：

- 不将 `PendingIntent` 序列化或上传；
- 一个通知更新后重新生成操作版本，旧版本操作请求应被拒绝；
- 多个 `RemoteInput` 或应用私有复杂输入在不兼容时标记为“不支持”，不能导致应用崩溃。

### AND-006 执行普通通知操作（P0）

Android 收到操作请求后：

1. 验证请求设备、通知 ID、通知版本和操作 ID；
2. 验证原通知仍存在；
3. 调用对应 `PendingIntent`；
4. 返回结构化结果。

结果状态至少包括：

- `accepted`：已提交给 Android；
- `succeeded`：本地调用未抛出错误；
- `notification_not_found`；
- `action_expired`；
- `action_unsupported`；
- `device_offline`；
- `permission_denied`；
- `internal_error`。

说明：Android 能确认 `PendingIntent` 被调用，但通常无法确认第三方应用最终业务结果（例如邮件是否真的被服务器归档）。界面文案应避免声称业务已最终完成。

### AND-007 执行文本回复（P0）

- Chrome 发送 UTF-8 回复文本；
- Android 将文本写入对应 `RemoteInput` 后触发 `PendingIntent`；
- 空文本默认不可提交；
- 默认最大长度 4,000 个 Unicode 字符，协议层和 UI 同时限制；
- 回复内容仅用于本次操作，不写入服务端日志；
- 防止重复点击造成相同回复多次发送。

### AND-008 远程清除通知（P0）

- 接收 Chrome 清除命令后调用 `cancelNotification(key)`；
- 对不可清除/持续通知返回明确失败。判据取平台对监听器单条取消的拒绝条件（`FLAG_ONGOING_EVENT`，即 `StatusBarNotification.isOngoing()`），不能用「清除全部」的语义（`isClearable()`，额外包含 `FLAG_NO_CLEAR`）代替——后者会把用户能划掉的通知也拒掉。失败通过 `ActionResult` 的 `INTERNAL_ERROR` 与说明性 `detail`（`NOTIFICATION_STILL_ONGOING`、`LISTENER_NOT_CONNECTED`）回报，发起方据此显示原因；
- 重复清除必须幂等；
- 清除成功后广播最终删除状态，确保所有在线 Chrome 一致；离线 Chrome 重连后通过删除墓碑或快照对账清除；
- 来自多个 Chrome 的清除请求按同一通知全局主键幂等处理。

### AND-009 本地移除同步（P0）

当原通知由用户、系统或来源应用清除时，Android 向服务端发送删除事件。

要求：

- 删除事件携带通知 ID 和单调递增版本；
- 无法判断具体原因时使用 `removed_unknown`，不得错误声称是用户操作；
- Chrome 离线时，当前状态快照应防止旧通知在重连后复活。

### AND-010 后台连接（P0）

为了不依赖 FCM，Android 需要维持到自托管服务端的连接。

要求：

- 使用带认证的 WebSocket；
- 指数退避重连并加入随机抖动；
- 网络切换后自动恢复；
- 根据 Android 版本采用合规的前台服务，并显示低打扰常驻通知；
- 引导用户处理厂商电池优化，但不得声称能够绕过系统限制；
- 清晰显示“在线、连接中、离线、权限缺失、服务端不可达”等状态。

### AND-011 当前状态快照（P0）

在首次连接或服务端要求重新同步时，Android 上传当前可同步通知的 ID、版本和状态快照，用于双方对账。

- 快照应有上限，建议默认最多 200 条当前活动通知；
- 超限时按更新时间保留最新项并报告截断；
- 快照不是长期历史记录。

### AND-012 工作区设备（P0）

- 查看当前工作区 Android 和 Chrome 的数量、名称、类型和最近活动状态；
- 明确标识当前 Android；
- 只读展示 authority-signed 设备名称；
- 不允许重命名、批准、拒绝或移除其他设备；
- 不建立客户端本地别名或双轨名称。

## 5.2 Chrome 扩展

### CHR-001 安装、注册与成员批准（P0)

- 用户输入服务端地址；
- 通过实例管理员生成的一次性配对码或二维码提交 pending registration；
- 设备生成 E2EE identity 并提交持钥证明；
- 只有 Server 管理网页可以批准、拒绝或移除设备；Chrome 只能提交并查看当前设备的申请状态；
- 管理员批准后，客户端验证 authority-signed device certificate 和最新 signed roster；
- 默认订阅工作区内所有已授权 Android，不要求只选择一台目标设备；
- 查看工作区 Android 和 Chrome 的数量、名称、类型和最近活动状态；
- 只读展示 authority-signed 设备名称，不能重命名、批准、拒绝或移除其他设备。

凭据必须使用扩展本地存储；不得通过 Chrome Sync 同步敏感令牌。

### CHR-002 展示系统通知（P0）

收到新增事件后调用 Chrome Notifications API 创建系统通知。

显示内容：

- 来源 Android 设备名（始终显示，不因当前只有一台设备而省略）；
- 来源应用名和应用图标；
- 可用时显示通知头像；
- 标题；
- 正文摘要；
- 富媒体内容的 `[图片]` 文本占位符；
- 最多展示两个按用户规则选出的快捷按钮。

规则：

- 「清除」是否固定占用一个按钮由本地设置决定，默认开启；
- 关闭常驻清除时，两个槽位均由用户快捷规则选择；
- 用户规则可匹配结构化的文本输入能力，或按精确／包含模式匹配来源操作标题，并可限定来源应用；
- 标题匹配执行 Unicode 规范化、首尾空白清理和不区分大小写比较；「包含」模式必须由用户显式选择；
- 同一操作命中多个规则时只采用最高优先级规则，同一规则命中多个操作时保留来源顺序；
- 如果符合规则的操作不足以占满槽位，且仍有未直接展示的操作，则追加最低优先级的「更多」；不为填满按钮而任意展示未配置的操作；
- 「更多」和点击通知主体均打开同一个完整通知交互窗口；

通知展示规则：

- Chrome notification ID 由来源设备 ID 和通知 ID 共同派生；
- 更新事件复用固定 Chrome notification ID；
- 删除事件关闭所有 Chrome 上的对应系统通知；
- 缺失标题或正文时采用可理解的回退文案；
- 图标或头像下载、解密、解码失败不影响文本通知；
- 静默通知使用 Chrome 的静默展示能力；普通通知不播放自定义声音、不强制高优先级打扰。

### CHR-003 扩展弹窗通知列表（P0）

弹窗展示当前活动通知：

- 默认合并展示所有 Android 来源，并支持按来源设备筛选；
- 按更新时间倒序排列；
- 每项始终展示来源设备、应用图标、可用头像、应用、标题、正文、时间和在线/过期状态；
- 通知详情展示所有可支持的操作项、回复和从手机清除，不受系统通知按钮数量限制；
- Popup 与点击系统通知后打开的 interaction 页面共享同一详情 read model 和操作入口；
- 支持刷新当前状态；
- 空列表、离线、未配对、权限异常分别显示对应状态。

MVP 不提供历史搜索和分页归档。

### CHR-004 执行普通操作（P0）

- Chrome 必须展示并允许调用来源 Android 通知公开且系统可表示的操作项，例如“标记为已读”“归档”“删除”；
- Chrome 不得自行模拟来源应用未公开的操作；实际业务动作必须由来源 Android 调用该通知的原始 `PendingIntent`；
- 点击操作后立即禁用该按钮，避免重复提交；
- 显示“正在发送”；
- 操作命令只发送到该通知的来源 Android；
- 收到结果后显示成功、已失效、来源手机在线或离线、失败；
- 操作结果和 Android 随后的权威状态广播到其他 Chrome，使各端同步更新；
- 超时不应显示成功；
- 可安全重试的操作必须使用同一个幂等键；
- 不可证明安全重试时，提示用户确认后生成新请求。

### CHR-005 文本回复（P0）

- 点击“回复”打开或聚焦扩展弹窗；
- 显示目标应用和通知摘要，防止回复错对象；
- 输入框显示长度计数；
- 提交时二次绑定通知版本；
- 操作失效或通知已更新时拒绝发送，并提示重新打开最新通知；
- 成功提交后清空输入内容；
- 回复草稿默认仅驻留内存，扩展关闭后不保存。

### CHR-006 关闭与清除同步（P0）

需要区分关闭来源：

- 用户点击常驻「清除」按钮：发送远程清除命令；
- 用户主动关闭系统通知，包括关闭按钮、通知中心清除及浏览器可识别的其他用户关闭方式：发送远程清除命令；Chrome 无法进一步区分具体关闭控件；
- 用户点击完整交互窗口中的「从手机清除」：发送远程清除命令；
- 用户点击通知主体、来源操作或回复入口后，浏览器随之关闭通知：不得误发清除命令；
- 扩展因收到 Android 删除事件而调用 API 关闭：禁止回环发送清除命令；
- 扩展初始化清理孤儿通知：禁止默认删除手机通知；
- action click、body click 和程序关闭原因必须在异步处理前持久化，并由对应的 `onClosed` 事件消费；
- 无法确认关闭是否由用户触发时采用保守策略，不删除手机通知。

清除命令复用现有 operation idempotency、结果和 ACK 链路，但不是来源应用公开的 action，也不得伪造 action descriptor。Android 接受清除请求只表示本地 `cancelNotification(key)` 请求已发出；最终删除状态必须等待来源 Android 的权威 `notification.removed`。

### CHR-007 Badge 与状态反馈（P0）

- Badge 显示尚未点开查看的新通知数，可在设置中关闭；
- 只有用户点开某条通知的详情后，该条才标记为已查看；仅打开 Popup 浏览列表不标记任何通知，也不减少角标；
- 通知发生用户可见更新时可以重新计入；纯恢复、重复投递和无用户可见变化的 revision 不增加计数；
- 当前活动通知总数在 Popup 内显示，不使用 Badge 表达；
- 离线时使用文字和图标状态提示，不伪装为在线。

### CHR-008 Service Worker 生命周期恢复（P0）

- 扩展启动或 Service Worker 唤醒后从本地最小状态恢复映射；
- 连接断开后重新鉴权并请求增量/快照对账；
- 不要求 Service Worker 永久保持 WebSocket 活跃；
- 需通过 Chrome 当前稳定版验证 WebSocket 保活行为；若平台不可靠，采用定期唤醒 + 状态拉取作为降级方案；
- 不重复弹出已确认处理的事件。

## 5.3 Linux 服务端

### SRV-001 部署（P0）

至少提供：

- OCI/Docker 镜像；
- Docker Compose 示例；
- Linux amd64 与 arm64 架构镜像；
- 环境变量配置；
- 数据卷说明；
- `/healthz` 存活检查和 `/readyz` 就绪检查；
- 反向代理及 TLS 配置示例。

建议默认由 Caddy、Traefik 或 Nginx 终止 TLS；服务本体也可选择直接提供 TLS。

### SRV-002 私有实例初始化与管理员秘密（P0）

- 首次启动必须生成或要求设置高强度管理员秘密；
- 不提供默认公共密码，不允许空密码；
- 默认关闭公开注册，不提供“仅凭服务端地址即可注册”的接口；
- 只有管理员可通过本机 CLI 或按需启动的受保护管理端生成一次性设备配对码；
- 配对码绑定设备类型，可选绑定设备名称，默认 10 分钟过期、单次使用，并具有至少 128 bit 随机熵；
- 配对码只授予提交注册申请的资格，不替代设备独立长期凭据和端到端密钥校验；
- 管理接口默认只监听 Unix Socket/本机地址；如显式开放网络访问，必须另有强认证和 TLS；
- 管理员秘密不得由普通设备 API 使用，不得写入日志或客户端配置；
- 连续配对失败必须限速，避免对配对码和管理员入口进行暴力尝试。

### SRV-003 设备注册与撤销（P0）

设备类型包括 `android` 和 `chrome`。

每台设备拥有：

- 随机设备 ID；
- 所属私有工作区 ID；
- 用户可见名称；
- 设备类型；
- 独立长期认证凭据和端到端身份公钥；
- 申请时间和批准时间；
- 最近成功认证时间和最近活动时间；
- 拒绝或移除时间；
- 撤销状态。

最近活动时间最多每分钟为同一设备持久化一次。第一版根据这些时间显示「刚刚活动」「最近活动」「一段时间未连接」或「从未成功连接」，不声称严格实时在线。

Server 管理网页支持列出设备、重命名设备、生成限定类型的配对码、批准或拒绝申请、移除设备。新设备只能由管理网页批准；Android 和 Chrome 只能查看 authority-signed 工作区设备名称，不能重命名、批准、拒绝或移除设备。页面中的移除先执行 durable revocation 并保留阻止旧凭据重新生效所需的记录，不直接硬删除。CLI 继续承担恢复和低频维护能力。设备撤销后立即断开现有连接，并触发客户端侧工作区成员状态收敛。

### SRV-004 实时连接、扇出与消息路由（P0）

- Android 和 Chrome 使用 WebSocket；
- 心跳检测失效连接；
- 消息必须包含协议版本、消息 ID、来源、目标/接收者集合、类型和时间；
- 每台 Android 的通知事件扇出给私有工作区内所有已授权 Chrome；
- Chrome 发起的通知操作只路由到通知主键指定的来源 Android；
- Android 返回的操作结果及权威通知更新/删除事件扇出给所有 Chrome；
- 服务端为每个 Chrome 独立维护确认游标，不能因一台 Chrome 已确认就删除其他离线 Chrome 尚未确认的状态；
- 只有同一私有工作区内已授权设备可相互通信；
- 服务端只依据明文路由信封转发，不能解密业务载荷；
- 单条消息、设备数量、连接数和连接速率有可配置上限；
- 未知消息类型返回协议错误而非导致服务崩溃。

### SRV-005 离线队列与状态（P0）

MVP 采用“短期事件队列 + 当前状态快照”，不保存长期历史。

建议默认：

- 操作命令：目标离线时不无限排队；短期保留最多 30 秒，随后返回 `device_offline`；
- 通知新增/更新/删除事件：按接收 Chrome 独立保留确认状态，直至各 Chrome 对账或最多 24 小时；
- 当前活动通知状态：按来源 Android 隔离，最多保留 24 小时或由对应 Android 快照覆盖；
- 回复文本：目标离线时默认不落盘排队，直接失败，避免延迟误发；
- 所有保留时长可配置并有硬上限。

### SRV-006 幂等与顺序控制（P0）

- 每个事件有全局唯一消息 ID；
- 每个通知以 `(sourceDeviceId, notificationId)` 为全局主键，并具有来源设备内单调递增版本号；
- 每个 Chrome 保存自己的最近确认游标；
- 服务端去重重复消息；
- 旧版本更新不能覆盖新版本；
- 删除状态优先于更旧的新增/更新；
- 操作命令使用幂等键，结果可短期缓存。

### SRV-007 最小化日志（P0）

默认日志可以记录：

- 时间、消息类型、设备 ID 的脱敏形式；
- 连接、鉴权、路由和错误状态；
- 消息大小和处理耗时。

默认不得记录：

- 通知标题、正文；
- 回复文本；
- 完整认证令牌；
- 端到端加密密钥；
- 完整请求载荷。

### SRV-008 数据管理（P0）

- 提供清空运行数据和撤销全部设备的方法；
- 明确数据库文件、密钥和配置的备份范围；
- 升级前支持数据库迁移检查；
- 卸载文档说明如何彻底删除数据。

### SRV-009 本机管理端（P0）

- 管理网页由独立进程提供，不挂载到公开 relay Handler，authority private key 不进入 relay 热路径；
- 默认不启动且只监听 loopback，远程管理使用 SSH 端口转发或独立 HTTPS 管理域名；
- 使用只显示一次、短期、单次的一次性登录码建立仅存内存的短生命周期管理员会话；
- 登录码不得进入 URL、数据库、访问日志或支持包；
- 所有状态变更使用 POST、严格 Origin 校验、CSRF token 和独立限速；
- 页面使用严格 CSP，禁止第三方脚本、CDN、遥测、跨源读取和 framing；
- 提供实例概览、加入码签发、待批准设备、批准、拒绝、重命名和移除；
- 显示申请、批准、最近成功认证、最近活动和移除时间；
- 页面不读取或展示通知正文、回复和操作内容，也不显示完整设备 ID、裸角色枚举或 authority private key；
- authority rotation、workspace restore 和全量清理在 Alpha 继续通过本机 CLI 完成。

## 5.4 配置需求

### Android 设置

P0：

- 服务端地址；
- 提交加入申请、等待批准和移除当前设备；
- 连接状态；
- 通知访问状态；
- 启动/停止同步；

## 6. 核心业务流程

### 6.1 注册与集中式成员批准流程

```text
管理员通过服务端本机 CLI 或受保护管理端生成绑定设备类型的一次性注册配对码
  → Android/Chrome 提交配对码、认证材料、E2EE identity public key 和持钥证明
  → 服务端验证配对码、有效期、类型和使用状态，创建 pending device
  → pending device 不能收发业务消息
  → 管理员在 Server 管理网页显式批准设备并分配固定权限模板
  → workspace authority 签发 canonical device certificate，并发布递增 epoch 的 signed roster
  → 客户端固定 authority public key，验证 roster、certificate、identity key、角色和撤销状态
  → 客户端安全保存独立 transport credential 与自身 identity private key
  → 一次性配对码立即失效
```

一次管理员批准使设备成为工作区成员，不要求它与所有已有 Android／Chrome 逐一比较安全码。业务消息仍为每个授权 recipient 创建独立 HPKE envelope，不复制长期令牌，也不引入共享内容密钥。

### 6.2 新通知流程

```text
任一 Android 的 NotificationListenerService 收到通知
  → 过滤、规范化、分配通知实例 ID 和版本
  → 提取文本、应用图标、头像和操作描述；正文图片转为 [图片]
  → 为所有已授权 Chrome 加密载荷并发送 notification.upsert
  → 服务端鉴权、去重并扇出给每台 Chrome
  → 每台 Chrome 独立接收和确认
  → Chrome 按 (sourceDeviceId, notificationId) 更新本地列表并展示来源设备
```

### 6.3 回复流程

```text
用户在 Chrome 点击回复
  → 输入文本
  → Chrome 生成幂等键并发送 action.invoke
  → 服务端只路由，不解释业务载荷
  → Android 校验通知版本和操作状态
  → 注入 RemoteInput 并触发 PendingIntent
  → Android 返回 action.result，并在原通知变化时发送权威更新/删除
  → 服务端将结果和状态扇出给所有 Chrome
  → 发起 Chrome 展示结果，全部 Chrome 同步最终通知状态
```

### 6.4 Chrome 清除流程

```text
用户主动关闭 Chrome 通知或点击「清除」
  → Chrome 先持久化关闭原因，避免 action/body/programmatic close 回环
  → 生成幂等键并发送 action.invoke（dismiss_notification = true）
  → Android 验证发送者、通知 ID、exact revision 和可清除状态
  → NotificationListenerService.cancelNotification(key)
  → action.result 只确认本地清除请求已接受
  → Android 监听真实移除回调并发送 notification.removed
  → 服务端广播最终状态
  → 所有 Chrome 清理本地镜像
```

### 6.5 Android 清除流程

```text
任一 Android 通知被移除
  → Android 发送带来源设备 ID 的 notification.removed
  → 服务端记录 tombstone/最新版本并扇出
  → 所有 Chrome 关闭对应系统通知、移出活动列表
  → 各 Chrome 的程序化关闭不再反向发送清除请求
```

### 6.6 断线对账流程

```text
每台 Chrome 重连并提交自己的 last_ack_cursor
  → 服务端按该 Chrome 返回可用增量
  → 增量缺失或游标过期时分别请求各 Android 当前快照
  → 按 (sourceDeviceId, notificationId) + version 合并
  → 仅清理对应来源 Android 快照中不存在的旧活动项
  → 旧项仅静默恢复列表，默认不重新弹系统通知
```

## 7. 状态模型

### 7.1 通知状态

```text
ACTIVE
  ├─ 更新 → ACTIVE（version + 1）
  ├─ Android 移除 → REMOVED
  ├─ Chrome 请求清除成功 → REMOVED
  └─ 超出本地保留期 → EXPIRED_LOCAL
```

规则：

- `REMOVED` 是终态，但相同 Android `key` 后续可对应新的通知实例 ID；
- `EXPIRED_LOCAL` 只表示镜像缓存过期，不能据此删除手机通知；
- 服务端短期保留删除墓碑，避免旧更新使通知复活。

### 7.2 操作状态

```text
READY → SENDING → ACCEPTED/SUCCEEDED
                 ↘ FAILED
                 ↘ EXPIRED
                 ↘ UNKNOWN（超时，最终结果未知）
```

`UNKNOWN` 不得自动重试可能产生副作用的回复操作。

Envelope {

## 9. 安全与隐私需求

### SEC-001 传输安全（P0）

- 公网部署强制 TLS 1.2+，推荐 TLS 1.3；
- 客户端验证证书和主机名；
- 默认拒绝自签名证书；如允许导入自签名 CA，必须由用户显式操作；
- WebSocket 使用 `wss://`。

### SEC-002 私有实例准入与身份认证（P0）

- 服务端默认关闭公开注册；所有注册接口在没有有效一次性配对码时必须拒绝请求；
- 仅实例管理员能从本机 CLI 或等价受保护渠道签发配对码；
- 知道域名、IP、端口或工作区 ID 均不足以注册或建立连接；
- 每台设备使用独立凭据；
- 长期令牌至少 256 bit 随机熵，优先采用设备公私钥认证；
- 凭据可单独撤销和轮换；
- 服务端只保存不可逆令牌摘要或设备认证公钥；
- 鉴权失败响应不得泄露工作区或设备是否存在；
- 未配对访问、配对尝试和鉴权失败均受速率限制。

### SEC-003 集中式成员授权（P0）

- 服务端管理员是 workspace membership、device role 和 revocation 的信任权威；
- 注册只创建 pending device，管理员批准并签发 device certificate 后才能收发业务消息；
- 客户端固定 workspace authority public key，持久化最高 signed roster epoch，并拒绝回滚、同 epoch 分叉、无效签名和非 canonical encoding；
- Android 设备只能发布自己的通知，并且只能执行主键指向本机通知的操作；
- Chrome 可接收同一私有工作区内所有具有发送权限的 Android 通知，但不能访问其他工作区；
- Chrome 操作必须明确指定来源 Android，且双方 certificate role 必须允许对应方向；
- 撤销必须推进 roster epoch、停止后续 envelope fanout，并立即使 transport 连接失效；
- 服务端管理操作与普通设备 API 隔离。

### SEC-004 强制端到端加密（P0）

目标：即使服务端数据库被读取或服务端操作者查看既有流量，也不能直接获得通知正文、回复文本、操作详情、应用图标和头像。服务端管理员能够授权新设备，使其获得批准后的未来业务数据；该风险属于明确接受的产品信任边界，不得表述为可抵御恶意成员授权。

要求：

- E2EE 不可关闭；缺少加密能力或密钥协商失败的客户端不得同步业务数据；
- 每台设备生成不可导出的长期身份密钥；私钥仅保存在 Android Keystore 或 Chrome 本地安全边界内；
- 使用经过公开审查的标准原语和成熟库，不自创密码算法或协议；
- 新设备同时经过 pending registration、identity 持钥证明和服务端管理员批准；workspace authority certificate 与 signed roster 建立 E2EE 成员身份；
- authority private key 只签发成员和 roster，不作为业务内容解密密钥；其生成、保护、备份、恢复和轮换是发布门禁；
- Android 为每台已授权 Chrome 建立独立会话，或采用具备成员变更与密钥轮换能力的成熟群组协议；MVP 优先采用每接收设备独立加密，降低组密钥复杂度；
- Chrome 发往 Android 的回复和操作命令使用目标 Android 的端到端会话加密；
- 每条密文使用认证加密，包含唯一 nonce、发送者身份、接收者身份、通知版本和防重放信息；
- 服务端仅能看到工作区、路由设备、消息类型、时间、密文大小、游标以及实现路由和顺序控制所必需的最小元数据；
- 添加 Chrome 时，各 Android 与其建立新会话并发送当前活动快照；新 Chrome 不获得历史密文；
- 撤销任一设备后停止为其生成密文，并轮换受影响会话/发送密钥；
- 客户端必须展示成员来源、角色、批准时间和撤销状态；identity 变化必须由新 authority certificate 和更高 roster epoch 明确授权，不能仅凭目录字段静默替换；
- 设备 identity private key 丢失时重新注册并由管理员批准；服务端不保存可恢复既有业务明文的后门。

### SEC-005 防重放与防滥用（P0）

- 校验时间窗、消息 ID、序列号和过期时间；
- 操作请求必须绑定通知 ID、版本和目标设备；
- 同一幂等键只执行一次；
- 限制连接数、消息速率、正文长度、图片大小和队列长度；
- 畸形载荷不得导致服务进程或 Android 服务崩溃。

### SEC-006 本地数据保护（P0）

- Android 凭据和密钥使用 Keystore；
- Chrome 认证凭据和 E2EE 私钥使用 `chrome.storage.local`，明确其安全边界，不使用 Sync；如浏览器环境无法提供硬件保护，设置页必须提示本机用户配置文件被攻破时的风险；
- 服务端密钥文件权限最小化；
- 客户端默认不长期保存完整通知历史；
- 日志和诊断包默认脱敏，导出前提示用户检查。

## 10. 非功能需求

### 10.1 性能

在客户端和服务端网络正常、均在线时：

- 通知端到端延迟：P50 ≤ 1 秒，P95 ≤ 3 秒；
- 操作请求到 Android 接收：P95 ≤ 2 秒；
- 单条纯文本通知载荷建议 ≤ 32 KiB；
- 单条消息硬上限建议 256 KiB；
- 单实例初始容量目标：至少 10 台 Android + 10 台 Chrome、每分钟 100 个来源通知事件，并包含向所有 Chrome 进行 E2EE 扇出的开销；
- 服务端空闲内存目标 ≤ 128 MiB（具体按技术栈校准）。

### 10.2 可靠性

- 所有消息至少一次传递，客户端依靠幂等消除重复；
- 服务端重启后保留设备注册、游标和必要的短期状态；
- 网络抖动不造成重复回复或通知复活；
- 数据库写入采用事务，迁移失败时拒绝带病启动；
- 单条坏消息不能阻断后续消息。

### 10.3 兼容性

首版兼容范围确定为：

- **最低 Android 版本：Android 10（API 29）**；重点测试 Android 10、12、14、15 及开发期最新稳定版；
- Chrome 当前稳定版及前一个稳定版；
- Linux 服务端：主流 amd64/arm64 容器宿主机；
- 反向代理必须支持 WebSocket Upgrade。

选择 Android 10 的原因：它在通知监听、`RemoteInput` 和现代 TLS 能力上足够成熟，同时覆盖仍有实际使用量的旧设备；更低版本会显著增加后台存活、安全存储、通知结构和测试矩阵成本。若某项安全原语在 API 29 无法安全实现，应优先提高最低版本，不能为兼容而降低 E2EE 强度。

### 10.4 可维护性

- 三端共享版本化协议定义和测试向量；
- 消息类型、字段和错误码集中维护；
- 自动生成或校验协议模型；
- 服务端提供结构化日志；
- 所有发布物使用语义化版本；
- 数据库迁移可重复测试，并提供升级/回滚说明。

### 10.5 可访问性与本地化

- 控件具备可访问名称和键盘操作；
- 不仅用颜色表达在线/失败状态；
- MVP 至少提供简体中文和英文文案框架；
- 时间按客户端本地时区显示，协议统一使用 UTC。

## 11. 异常与边界情况

必须设计并测试：

1. Android 通知创建后立即删除；
2. 同一通知在一秒内高频更新；
3. 通知标题、正文为空或非常长；
4. Emoji、组合字符、RTL 文本和多语言回复；
5. 分组通知、媒体通知、持续通知、前台服务通知；
6. 来源应用没有操作项；
7. 操作项标题重复；
8. 用户点击操作时通知已更新或删除；
9. `PendingIntent` 被取消或抛出异常；
10. Chrome 用户连续点击同一按钮；
11. Chrome 程序化关闭触发关闭回调，形成删除回环；
12. Chrome Service Worker 在处理中被挂起；
13. 手机断网、切换 Wi-Fi/蜂窝网络、休眠、省电模式；
14. 服务端重启、数据库暂时不可写、磁盘已满；
15. 客户端时钟严重偏差；
16. WebSocket 经反向代理空闲超时；
17. 同一私有工作区的多个 Chrome 同时操作；
18. 设备被撤销但旧连接仍存在；
19. 大图标或恶意压缩图片；
20. Android 重启后本地 `PendingIntent` 映射全部失效。

## 12. 可观测性与诊断

### 12.1 用户可见诊断

Android 和 Chrome 均显示：

- 客户端版本与协议版本；
- 服务端地址；
- 配对状态；
- 最后成功连接时间；
- 最后一次消息发送/接收时间；
- Android 通知权限状态；
- 最近一个错误码和简短处理建议。

### 12.2 服务端指标

建议暴露可选 Prometheus 指标，但不得包含通知内容：

- 当前连接数；
- 连接/鉴权失败数；
- 按消息类型统计的路由数；
- 消息延迟；
- 队列长度和丢弃数；
- 数据库错误；
- 进程资源使用情况。

### 12.3 隐私要求

- 遥测默认关闭；
- 不向项目方发送任何指标；
- 用户启用的指标仅在自己的服务端本地暴露；
- 诊断包导出前进行令牌、正文、回复文本和公网地址脱敏。

| E2E-04 | 通知支持回复 | Chrome A 输入文本并提交 | 来源 Android 通过 RemoteInput 调用原操作；服务端和日志均无法读取回复文本 |
| E2E-05 | 通知可清除 | 用户关闭 Chrome A 的系统通知 | 来源 Android 通知被清除，Chrome B 等其他 Chrome 同步消失 |
| E2E-06 | 通知已镜像 | 用户在来源 Android 清除通知 | 所有 Chrome 的对应系统通知和活动项消失 |
| E2E-07 | 来源 Android 离线 | Chrome 尝试回复 | 明确标明具体离线设备，不延迟发送该回复 |
| E2E-08 | 两台 Chrome 持有同一旧版本 | 两端近同时操作 | Android 串行校验；状态变化后的旧版本操作不再执行 |
| E2E-09 | 多端存在不同确认游标 | 服务端重启并自动重连 | 各 Chrome 独立补齐，最终状态一致且不重复弹出全部旧通知 |
| E2E-10 | Chrome Worker 重启 | 扩展恢复 | 无删除回环、无重复操作、状态可恢复 |
| E2E-11 | 同一消息重复投递 | 人为重放消息 | 通知不重复，同一幂等操作最多执行一次 |
| E2E-12 | 撤销 Chrome 设备 | 旧扩展继续连接 | 立即断开且无法读取新通知；其 E2EE 会话被轮换 |
| E2E-13 | 通知含应用图标和头像 | Android 发布通知 | 所有 Chrome 正确显示；解码失败时安全回退 |
| E2E-14 | 通知正文含图片 | Android 发布通知 | 不传输正文原图，Chrome 在对应位置显示 `[图片]` |
| E2E-15 | 静默/持续通知各一条 | Android 发布通知 | 静默通知被静默同步；持续通知按默认规则不被同步 |
| E2E-16 | 未持有配对码的客户端 | 尝试注册或连接 | 服务端拒绝且不泄露工作区和设备信息 |

### 13.2 安全验收

- 抓包、服务端内存、日志和数据库均不能获得通知、操作、回复、图标或头像的业务明文；
- 重放已执行的回复请求不会发送第二次；
- 伪造另一设备 ID 无法访问通知；
- 日志扫描不包含标题、正文、回复文本和完整令牌；
- 过期配对码和已使用配对码均不可复用；
- 超大、畸形和未知协议消息被拒绝且服务保持可用。

### 13.3 发布阻塞缺陷

以下缺陷必须阻塞 MVP 发布：

- 回复可能被发送给错误通知或错误联系人；
- 单次点击可能产生多次回复/操作；
- 程序化关闭 Chrome 通知误删手机通知；
- 未授权设备可读取通知或执行操作；
- 日志泄露通知正文、回复或凭据；
- 断线重连大量重复弹出旧通知；
- 服务端常规重启导致配对或状态不可恢复；
- 任何允许关闭 E2EE、静默降级到明文或让服务端持有解密密钥的路径；
- 未持有有效配对码的陌生设备可以注册或连接；
- 多 Android 通知 ID 冲突，或一台 Chrome 的清除未同步到其他 Chrome。

## 14. 研发拆分与里程碑

### 阶段 0：技术验证（建议 1–2 周）

交付：三个独立原型，先验证最高风险，不追求完整 UI。

1. Android 能提取目标应用通知按钮并调用 `PendingIntent`；
2. Android 能使用 `RemoteInput` 完成至少两个主流应用的回复；
3. Chrome MV3 能可靠接收消息、展示通知并识别用户关闭事件；
4. Chrome Worker 休眠/恢复后的 WebSocket 或降级轮询方案可行；
5. Android 在不使用 FCM 时的前台服务、待机和厂商省电行为可接受；
6. 两台 Android 到两台 Chrome 的扇出、来源标识和跨 Chrome 清除闭环可行；
7. API 29 上可安全实现选定 E2EE 方案、密钥存储和设备身份验证；
8. 应用图标、会话头像可被规范化、安全压缩并在 Chrome 展示。

退出条件：确认核心链路可行，并记录不兼容应用和平台限制。

### 阶段 1：协议与最小贯通

- 冻结协议 v1 基础信封、通知模型和错误码；
- 服务端私有注册、WebSocket 鉴权和多接收者路由；
- 强制 E2EE 身份建立和每接收设备加密；
- 多台 Android 上传普通文本通知、图标和头像；
- 多台 Chrome 展示、来源区分与更新通知；
- 建立三端协议契约测试。

退出条件：至少 2 台 Android + 2 台 Chrome 在线时可稳定完成新增、更新、删除和独立确认。

### 阶段 2：操作闭环

- 普通操作；
- 文本回复；
- Chrome 主动清除并广播最终状态；
- 多 Chrome 并发操作的串行校验；
- 幂等、版本校验、超时和结果回传；
- 删除回环防护。

退出条件：E2E-03 至 E2E-08 通过。

### 阶段 3：可靠性与持久化

- 短期队列、游标、墓碑、快照对账；
- 服务端重启恢复；
- Android/Chrome 自动重连；
- Worker 生命周期恢复；
- 限流、消息大小限制和错误隔离。

退出条件：断网、重启和重复投递测试通过。

### 阶段 4：安全与自托管发布

- 私有实例初始化、配对码、设备撤销、凭据轮换；

- 可访问性；
- 发布检查清单、已知限制和故障排查文档。

## 15. 代码仓库结构

项目从开始即拆分为三个独立 Git 仓库，未来分别推送到 GitHub：

```text
notification-mirroring/     # 本地协调工作区，仅保存跨项目文档
├─ server/                  # Linux 服务端独立 repo；协议权威来源
├─ chrome-extension/        # Chrome Manifest V3 扩展独立 repo
├─ android/                 # Android 应用独立 repo
└─ docs/                    # 当前工作区中的 PRD/实施计划
```

协议 schema、错误码和测试向量以 `server` 仓库发布的协议版本为权威来源；Android 和 Chrome 仓库保存固定版本的 vendored 副本及上游 tag/SHA-256，不依赖本地相对路径。跨仓库协议变更必须先发布协议版本，再由两个客户端显式升级。三个仓库均需拥有独立 README、当前 `GPL-3.0-only` License、非追溯许可证切换说明、CI、版本和可复现构建方式；切换边界及以前已发布的 MIT 授权保持有效。

具体技术栈和多仓库协作流程参见实施计划，并通过 ADR 记录后续调整。

## 16. 风险分析

| 风险 | 影响 | 缓解措施 |
|---|---|---|
| Android 厂商杀后台 | 手机离线、通知延迟 | 合规前台服务、明确状态、电池优化指引、兼容性矩阵 |
| 不同应用通知操作实现不一致 | 回复/归档失败 | 技术验证、能力检测、版本绑定、明确失败和已知兼容列表 |
| Chrome MV3 Worker 挂起 | 实时连接不稳定 | 验证 WebSocket 行为；事件游标、重连、定期拉取降级 |
| 用户关闭事件语义不可靠 | 误删手机通知 | 跟踪程序化关闭；不确定时保守不删；专项自动化测试 |
| 至少一次投递造成重复副作用 | 重复回复或归档 | 幂等键、服务端结果缓存、Android 本地执行去重 |
| 自托管配置复杂 | 用户无法完成部署 | 单容器/Compose、反代示例、健康检查和可操作错误提示 |
| E2EE 多设备成员管理复杂 | 新设备无法加入或被撤销设备继续接收 | 服务端 authority certificate、signed roster epoch、独立设备 identity、每 recipient 加密、撤销和互操作测试向量 |
| 服务端被陌生人注册滥用 | 资源消耗、隐私与安全风险 | 默认关闭公开注册、本机管理员 CLI、短期单次配对码、限速和设备撤销 |
| 多 Chrome 状态竞争 | 状态不一致/重复操作 | 全局通知主键、Android 串行校验、版本绑定、每客户端游标和最终状态广播 |
| 图标与头像增加攻击面 | 内存、解码漏洞 | Android 端规范化、尺寸/MIME/字节上限、静态首帧、Chrome 安全回退；正文图片仅显示占位符 |

## 17. 已确认产品决策

1. **设备规模**：MVP 原生支持多台 Android 和多台 Chrome，各 Android 独立选择接收浏览器，同步范围以第 2.5 节为准。
2. **来源标识**：每条通知始终显示来源 Android，协议主键包含来源设备 ID。
3. **端到端加密**：E2EE 是不可关闭的 P0 发布条件，服务端不持有业务解密密钥。
4. **实例准入与成员授权**：默认关闭公开注册；短期单次配对码只创建 pending device，服务端管理员批准后由 workspace authority certificate 和 signed roster 建立成员身份。管理员可授权恶意新设备读取批准后的未来数据，这一风险明确接受。
5. **Android 最低版本**：Android 10（API 29）。
6. **媒体范围**：同步应用图标和可读取的通知/会话头像；通知正文图片不传原图，使用 `[图片]` 占位。
7. **持续与静默通知**：持续/前台服务通知默认不同步，允许后续按应用开启；静默通知默认同步并在 Chrome 静默展示。
8. **Chrome 关闭语义**：只有确认由用户主动关闭时才请求清除来源 Android；Android 成功后向所有 Chrome 广播最终删除。
9. **离线回复**：不排队，来源 Android 离线时立即失败。
10. **账号模型**：MVP 不做公开账号注册，采用一个私有工作区、管理员 CLI、pending device 审批和集中式成员授权。
11. **许可证**：当前版本为 `GPL-3.0-only`，允许商业使用，分发 GPL 覆盖版本时必须遵守 GPLv3；许可证仅从各仓库记录的切换边界之后生效，既有 MIT 授权不追溯、不撤销。
12. **服务端数据库**：个人自托管 MVP 优先采用嵌入式数据库，避免强制依赖外部 PostgreSQL；具体实现在技术设计阶段通过 ADR 确定。

## 18. MVP Definition of Done

只有同时满足以下条件，MVP 才算完成：

- 三端均有可复现构建方式；
- 用户可从空白 Linux 主机按文档完成部署、注册设备、管理员批准和测试通知；
- 至少以 2 台 Android + 2 台 Chrome 验证新增、更新、Android 删除、任一 Chrome 清除和全端状态收敛；
- 每条通知始终标明正确的来源 Android，跨设备通知 ID 不冲突；
- 应用图标和可用头像完成 E2EE 同步，正文图片仅显示 `[图片]`；
- 至少在两类主流应用上验证普通操作，在两类支持 `RemoteInput` 的应用上验证回复；
- 手机离线、任一 Chrome 重启、服务端重启后系统能恢复到一致状态；
- 操作具备通知版本绑定、幂等保护和多 Chrome 并发校验；
- 未授权设备不能注册，E2EE 全程强制且服务端无法读取业务明文；
- 安全验收与全部发布阻塞项通过；
- 文档明确权限、数据流、保留周期、已知限制和卸载清理方式；
- 仓库包含 `GPL-3.0-only` License 和精确的非追溯 MIT→GPL 切换边界，且不包含付费解锁、项目方云依赖或未披露遥测；
- 不把非核心功能带入 MVP。
